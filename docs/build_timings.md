## 1. 时刻是解码的，分类是规则的

| 项 | 性质 | 来源 |
|---|---|---|
| 购买时刻 | **解码（file-decode）** | `BUYEQUIP` 帧号 → `(frame−1)/15 s`，误差 ≤ 1 帧（≈67 ms） |
| 装备 ID / 名称 / 价格 | **解码 + 表对照** | 帧命令里的 `equip_id`，价格查 `agent_equip_prices.csv`（732 项） |
| 成品/散件 | **规则判定** | 价格阈值 ≥1000 且非鞋 |

价格分界来自本局实际购买：135 笔首次购买里，≤399 有 57 笔（基础散件）、
700–999 有 53 笔（中间件）、1500+ 有 25 笔（成品）、**1000–1499 一件都没有**。
所以 ≥1000 在本局不会误判。

## 2. 两种常见口径都给

「三件套」在赛训语境里口径不一，所以同时输出三个变体：

| 口径 | 含义 |
|---|---|
| `noShoes`（默认） | 三件核心成品，鞋子不计 |
| `withShoes` | 升级鞋（≥500）也算一件 |
| `bigOnly2000` | 只数 ≥2000 的大件 |

例：百里守约三种口径分别是 10:49 / 8:42 / 10:49；钟馗是 9:26 / 5:42 / —
（他的辅助装 1900 没到 2000）。**差额本身就说明口径必须先统一再比较。**

## 3. 已知局限

1. **没有商店合成树**：本地没有「散件→成品」的配方表，所以「成品」只能按价格判，
   不能按客户端自己的分类判。换客户端版本后必须重新核对阈值。
2. **二级打野刀、二级辅助装**这类 750–1100 的「半个成品」在阈值附近，本局没有出现，
   但换局可能误判。
3. **累计花费会高估**：`goldSpent` 是把首次出现的购买价累加，散件升级成品时
   散件价和成品价都被计入。三件套时序不受影响（只取成品事件本身），但
   「花费」不能当「金币收入」用。
4. **成品被卖再买**：`SELLEQUIP` 在本样本 0 条，若后续出现需要重算。

### 0.2 全局排序原则（五条）

1. **身份与口径先行**：战队合并、选手认领、英雄标签/改名是几乎所有下游分析的键（"本队 / 对面 / 自家选手"都要靠它们定义）。键错了，后面做得再漂亮也是错的。
2. **核心优先于周边**：教练在原文中明确"10 人面板 / 对位是全软件核心、立身之本"（原文 90–92、105–110 行）。对局模块虽在简报清单中列在英雄之后，本稿**提前到批次 1**。
3. **快赢穿插**：术语纠正、红蓝配色、秒数改分秒、删无效指标等小改动零风险、见效快，放在批次 0 一起交付，用于建立信任。
4. **数据闸门约束**：依赖 `draftEvents`（逐手 BP）、`version`（补丁标识）、回放覆盖率的分析，只能做到"有数据才出结论"，不得编造（`docs/bp_intelligence_roadmap.md` §数据闸门）。
5. **删除先于新增**：教练明确要求删 360 图、体系雷达图、最长集结秒、21 个资源控制等。删除是低风险改动，应在对应批次开头完成，避免新旧两套并存造成误读。

### 0.3 优先级定义

| 级别 | 含义 |
|---|---|
| **P0** | 核心必做。不做则软件价值不成立（身份正确性、10 人面板）或属于口径错误必须纠正 |
| **P1** | 重要。教练明确要求、影响日常使用，但可排在核心之后 |
| **P2** | 增强 / 长期。依赖数据积累或算法复杂度高，可放到后期 |

## 2. 分批实施计划

### 批次 0 · 地基批（P0，前置）

**目标**：先把"键"和"口径"校正，让后续所有分析建立在正确的战队 / 选手 / 英雄身份与统一术语上；同时交付零风险的快赢改动。

**包含哪些点**

1. 战队合并：换人 / 转会 / 离队重合识别，产出**候选**而非直接写入；人工确认合并，全程 `change_log`（entity=`team_merge`），可撤销。
2. 选手认领：游戏名 → 选手 ID 映射；小号合并同样走人工确认，不自动归并。
3. 英雄标签可编辑（在既有 `docs/hero_labels_import_2026-11.md` 导入结果之上开放编辑入口）；公共英雄改名（改名保留别名映射，历史统计按 ID 不按字符串）。
4. 自定义组合清单导入：赛训组给文档 → 导入修正当前排位数据导致的组合不准（原文明确"扁鹊+元府不搭"）。
5. 术语 / 口径统一（全站批量）：法核→法刺、BO→训练赛（大场下必须标小局数）、对位众生→入侵时长、秒数→"X 分 Y 秒"、分阶段文字→"0–4 / 4–10 / 10–结束"、英雄分类结构专业化。
6. 采集部署基础：U 盘离线导入方案落地；录像由"必选"调整为"非必选"（审核门槛二选一，沿用 `docs/collection_sop.md` 口径）；10 分钟经济纳入必采字段，并把赛训组提供的**10 分钟标准经济门槛**替换掉错误的"1 万经济"。

**先后顺序理由**

- 战队合并 → 选手认领：选手归属依赖战队身份定稿；顺序反了会产生"先把人认到错队，再合并队"的二次污染。
- 选手 / 战队身份 → 英雄标签 / 组合导入：组合是"本队 vs 对面"口径，身份未定则无从判断哪边是"本队"。
- 口径统一放在本批：它是纯文本与枚举改动，风险最低、见效最快，且能避免后续批次按旧术语开发再返工。
- 采集基础放在本批：10 分钟经济门槛是批次 1 面板"达标判定"的输入；U 盘与录像非必选决定数据覆盖率，越早明确越好。
- **前置依赖**：系列赛编组已由其他成员完成，本批直接复用，不重复建设。

**前后端落点估计**

| 端 | 预计落点（实现时确认） | 工作量感觉 |
|---|---|---|
| 后端 | `identity_service.py` / `identity_auto.py` / `identity_rules.py`（合并与认领候选、人工确认、变更日志）；`hero_archetypes.py` / `hero_catalog.py` / `hero_names.py`（标签编辑、改名别名）；`combo_pool.py` + `data/facts/kpl_combos.json`（组合导入）；`server.py` 挂载新 API；`collection_contract.py` / `channel_store.py`（U 盘 / 录像门槛 / 10 分钟经济字段） | 中（多为数据治理与 CRUD，合并识别逻辑略重） |
| 前端 | `v3/public/app.js` / `features.js`（新入口挂载）；`config-tools.js` 或新增 `identity-tools.js`（合并 / 认领确认界面）；`grade-rules.js` / `combo-pool.js`（标签 / 组合编辑）；`capture-page.js`（U 盘 / 门槛）；术语批量替换散落在各页 JS 与 `index.html` | 中 |

**风险**

- **误合并不可回滚**：必须软合并（保留原 ID 映射 + 变更日志 + 撤销入口），严禁物理删除；推荐先出"候选列表"给教练逐条确认。
- **小号误并 / 认错队**：污染选手档案与后续所有画像。需双人复核或"先标记待确认、不影响统计"的灰度策略。
- **英雄改名影响历史统计**：必须按 ID 聚合，字符串只作展示；改名后全量回归检查统计口径不变。
- **口径统一牵一发动全身**：术语替换可能波及文案、图表标题、验收脚本（`scripts/verify_*.py`），需一次性全量 grep 回归。
- **U 盘方案依赖现场执行**：离线导入的素材完整性、版本冲突、重复导入需有校验规则，否则脏数据会冲进批次 1。

### 批次 1 · 对局核心批（P0）

**目标**：交付教练定义为"全软件立身之本"的 10 人面板与对局呈现改造，做到"一针见血、一眼见血"。

**包含哪些点**

1. **★10 人面板重做**（最高优先级）：卡片式；卡面第一视觉是结论（"⚠ 转输出异常 · 本局 2 项异常"）而非数字；偏差条以对面为 0 点，高于向右绿、低于向左红；最异常项自动置顶、放大、红框；红/黄/绿灯 + 大号差距数字；明细按需下钻。核心字段：10 分钟经济、整局分均经济、输出（%）、参团率、经济转输出（必须达标 / 未达标 + 优秀/良好/异常三档）。整体经济、10 分钟经济、分均支持手动填写。
2. 双方阵容扩大 + 出装进阵容（英雄比拼术语按"战士/打野"专业结构，去"法核"）。
3. 红蓝 buff 控制率拆分：原"资源 + 建筑"混排改为"防御塔 / 红蓝 buff"两类分开；保留集结率、集结次数，删最长集结秒；"偷野怪统计"难度高，明确不做并在界面说明。
4. 兵线只做前 4 分钟三路（其余时长模块不裁剪）；分阶段标签改具体时间分段。
5. 入侵口径统一（指标名"入侵时长"，时间口径 0–4 / 4–10 / 10–结束）。
6. 走位热点：标红蓝 buff、图标细节优化；半区 / 深区定义写清；半区秒数改"X 分 Y 秒"。
7. 单局 / 大场改名："几场训练赛"，"BO 几"下标注；大场下标小局数（如 11 个大场 / 18–14 小局）。**依赖已完成的系列赛编组**。
8. 标注取代"关注"（教练自写标签 + 标红 + 点开定位到时间点）。
9. 事件呈现改版：切 C 突出次数 + 对面头像、首杀改"一血"、击杀直接列大字号；推塔 / 水晶与关键资源（暴君 4/8/10/14/18 分钟、20 分钟风暴龙王）改"时间直线 + 标注"，鼠标移入看详情、可隐藏，圈圈换暴君图标；"21 个资源控制"改一句话总结（暴君放几个、塔/水晶推几座、首推时间放下）。
10. 赛后板块：分均输出改百分比；对手对比不如我方项标红框/标色。
11. 大屏红蓝配色 + 本队字体放大。
12. 查询 / 筛选 / 战队名称联动（依赖批次 0 战队合并）。

**先后顺序理由**

- 放在批次 0 之后：10 人面板的"达标判定"要吃 10 分钟经济与标准门槛，红蓝 buff / 入侵口径要吃口径统一，改名要吃系列赛编组——都是本批前置。
- 10 人面板排本批第一：教练反复强调它比其他所有花样都重要，先把它做对再铺周边。
- 删除项（最长集结秒、21 个资源控制、条状切 C）在对应模块改造开头完成，避免新旧呈现并存。
- 视觉类小改（红蓝配色、字体、标色）最后做，可在同一批内快速收尾。

**风险**

- **"一针见血"是主观验收标准**：必须先出 1–2 张卡面原型给教练确认，再铺全量；否则返工成本极高。整理纪要 §7 已给出可落地的五条改造方案，建议按其做原型。

- **性能**：偏差条与异常判定需全量重算，沿用 `docs/series_builder.md` 的指纹缓存思路，避免每次进页卡 4–7 秒。
- **批量改名回归蛋白**：BO→训练赛涉及大量文案与验收脚本，需一次改透。

## 4. 跨批次口径纪律（硬性，全部批次共用）

1. **不造假**：缺数据显示「—」或空态说明，不用 0 充数；样本 <3 局不给胜率 / 趋势结论。
2. **分源不混池**：训练赛与 KPL 分别计算、分别标注；KPL 是外部参照，不是官方英雄榜。
3. **关联不是因果**：反制 / 应对 / 组合胜率一律写"历史共现"，不写"该 ban 谁 / 一定克制"。
4. **证据可追溯**：每条结论带 `matchKey`，可点进 `#match/<key>`；禁止 `#match/null`。
5. **手序分层**：只有显式 `draftEvents` / `bpOrder` / 人工录入才标"已核验"，按营地名单套模板的标"假设"，不把模板当逐手核验。
6. **删除先做完**：最长集结秒、21 个资源控制、360 图、体系雷达、旧"关注"、条状切 C，在对应批次先删后建，避免双轨并存。

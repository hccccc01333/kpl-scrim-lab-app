# 打野位置口径:过河时间与首次过河

- 版本:2026-11-10(平台 1.5.29)
- 数据:`data/official_replays/camp-<seq>/positions.json`,**1 Hz 逐秒坐标**,每人每局约 660 点
- 用途:给「打野节奏」这张卡定口径。**先定死再算,不算完再解释。**

---

## 1. 坐标与半区怎么定

| 项 | 结论 | 依据 |
|---|---|---|
| 坐标范围 | x、y 约 −53 ~ +53 | `data/map_calibration.json`(取本批回放的 1%–99% 分位) |
| 双方基地 | 蓝方在负对角、红方在正对角 | 实测:蓝方五人前 30 秒的 (x+y)/2 ≈ −30,红方 ≈ +28 |
| 半区分界线 | **x + y = 0** | 基地连线是 (1,1) 方向,垂直平分线就是 x+y=0 |
| 过河值 | `e = (x+y)/2 ×(蓝方 +1,红方 −1)` | e > 0 即在对方半区 |

> 这条轴是**对角线投影**,不是「屏幕上下」。五个人都用同一套。

## 2. 「过河」与「入侵」不是一回事

- **过河**:e > 8,人已经越过河道中线。
- **深入**:e > 25,进到对方野区腹地。

**为什么要分开**:打野过河有一半是去抓人(经过河道、边路),不等于进野区反野。
我们试过直接叫「入侵时长」,数据不支持——同一局里打野 e>8 的时间占 25%,
但 e>25 只有 0.8%,把两者混成一个「入侵」会让数字虚高、教练照着排训练会排错。

所以这张卡只叫**过河**,并且把「反野次数」交给另一套更硬的证据:
回放里的 BUFF 击杀事件(`buffEvents`,`owner` 是被反的一方)。

## 3. 每个人怎么对上

| 步骤 | 做法 | 验证 |
|---|---|---|
| 位置数组顺序 | 与 `raw.matchInfo[]` 完全一致 | 24 局逐局比过 `playerId` 序列,全部一致 |
| 阵营 | 前 5 蓝、后 5 红 | `matchInfo[].acntcamp` 恒为 `11111 22222` |
| 打野索引 | 比赛详情 `players[i].position == '打野'` 且 `camp` 为本队 | 详情顺序与 matchInfo 同源,同一索引 |
| 回放目录 | `match_detail.officialReplay.id` = `camp-<seq>` | 无需查 channels 表 |

**已知风险**:详情 `players[].playerId` 常为空,所以只能靠「顺序」对齐,不能靠 ID 对齐。
如果哪天详情顺序变了,这张卡会错位——所以这里写死验证方法:顺序比对 `matchInfo` 的 playerId。

## 4. 指标定义

| 指标 | 公式 | 说明 |
|---|---|---|
| 统计窗口 | 开局 0–600 秒 | 只看前期,后期打野本来就在全场跑 |
| 过河时间 | `e > 8` 的秒数 | 1 Hz,一秒一点,直接计数 |
| 过河占比 | 过河秒数 / 有效秒数 | 分母是实际有点的秒数,不是恒定的 600 |
| 首次过河 | 第一个 `e > 8` 的秒 | 没有则留空 |
| 深入占比 | `e > 25` 的秒数 / 有效秒数 | 单独给,不合并 |
| 反野次数 | BUFF 事件里 `owner=对方 且 killer=我方` 的条数 | 来自 `buffEvents`,不是位置推算 |

## 5. 不做什么

- **不把过河叫成入侵**,也不把深入当唯一标准。
- **不推断意图**:过河可能是抓人、可能是反野、可能是回城路过。
- **不做路线聚类**:样本里同一打野的局数不够,聚类出来的是噪声。
- **不补零**:没有位置文件的局,整张卡显示「没有位置数据」,不进分母。

## 6. 这张卡能回答什么

- 我们的打野前期在不在对方半区?占比多少、第一次过河多早?
- 赢的局和输的局,过河时间差多少?(和反野次数并排看)
- 如果过河很多但反野很少 → 过河是在跑,不是在反野,该改路线。

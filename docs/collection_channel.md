# 一局采集通道（kpl-collection-channel-v1）

采集通道把“同一局的全部采集材料”放在一个固定容器里，不再让截图、表格、录像和回放各自散落。**一局一个通道 ID**；来源统一关联到同一局。通道有两种录入方式：**营地录入**（默认，要求营地链接）和 **OCR 新录入**（王者营地拿不到的老局，用七页截图或一段录屏直接建档，不要求营地链接）。表格、回放文件选填。详细操作与示例见 [采集 SOP](collection_sop.md)。

## 两种录入方式：补采 ≠ 新录入

王者营地只保留约一个月的对局详情，更早的局在营地侧已经没有入口。因此截图 / 录屏有两种完全不同的用途：

| 用途 | 什么时候用 | 动作 | 审核口径 |
| --- | --- | --- | --- |
| **补采** | 通道已经存在（通常是营地同步建的），只是缺截图 / 录屏素材 | 在截图 OCR / 录屏 OCR 页选一个已有对局，把素材挂上去 | 营地通道口径不变：营地链接必采，营地面板 / 七图+录屏 二选一 |
| **新录入一局** | 超过一个月、营地没有详情，或者根本没走营地采集的老局 | 从识别结果直接「新建一局并录入」，建好后进校对页核对保存 | OCR 通道口径：七页截图齐全 **或** 一段十人阵容完整的录屏报告，任一即可 |

- 通道字段 `entry.mode` 标记录入方式（`camp` / `ocr`），`sourceStatus.mode` 同步返回；旧通道没有该字段时自动推断：有营地链接算 `camp`，否则已有截图/录屏算 `ocr`。
- 新录入时自动带出能识别的比赛信息：日期、时长、比分、模式；截图默认按「左列 = 我方」解释胜方，录屏按 POV 阵营判断我方在左还是右。校对页的「本局信息」卡可以再改。
- 同一组截图 / 同一份录屏重复新建会返回 409；已补采过的素材在页面上有徽标，避免重复建档。

## 通道状态机

```text
创建通道
  ↓
放入来源：缺失 → 已上传/已解析 → 已完成
  ↓
生成跨来源草稿（字段、来源、冲突、缺失）
  ↓
人工审核（复核人 + 时间 + 修改日志）
  ↓
保存 kpl-match-data-v1 数据包到 data/matches/
  ↓
分析平台 /analysis 读取该局
```

来源状态：

| 状态 | 含义 |
| --- | --- |
| `missing` | 还没有放入 |
| `parsed` | 已解析（表格、截图、回放） |
| `partial` | 已放入一部分（尚无完整录屏报告） |
| `completed` | 该来源已达到要求 |
| `failed` | 解析失败，保留原文件供重试 |

**营地录入**的唯一必采是本局营地网页回放链接；**审核门槛二选一**：① 营地自动同步导入十人面板（推荐主路径）；② 补齐七种截图 + 一份录屏报告（传统兜底）。`sourceStatus.complete` 按这条双合规口径判定。未满足可保留草稿，不能审核或保存；表格与回放文件始终选填。

**OCR 新录入**不要求营地链接：七种截图齐全，或一段十人阵容完整的录屏报告，任一即可审核保存。两条路径都允许后续再补另一类素材（例如先用截图建档、之后补录屏补过程时间轴）。

## 六类来源的固定字段

| 来源 | 放置内容 | 固定提取/贡献 | 不能提供 |
| --- | --- | --- | --- |
| 王者营地（营地录入必采） | 本局 `camp.qq.com` 网页回放链接，成功提取并关联 | 官方约 30 秒金币、事件和逐秒位置 | 逐秒金币、完整逐人输出/承伤 |
| 营地十人面板（推荐） | 教练号扫码授权后按选手增量拉取的 `battledetail` | BP、十人 KDA/经济/输出/承伤/参团/评分，以及补刀、野怪经济、治疗、控制、对塔伤害、伤害转化比、每死承伤、等级、最终出装 | 过程时间轴、逐帧位置；旧版详情可能缺扩展字段（按缺失处理） |
| 表格（选填） | 项目标准十人模板 CSV/XLSX，1 份或多份 | 按项目单局字段约束校验；可补 KDA、经济、输出、承伤、参团、评分和英雄 | 不自动证明同一局；不自动绑定选手 ID |
| 录像 | 一段完整录屏生成的一份 JSON 报告；补采或新录入都可用 | 十人英雄/昵称、时间轴、团队金币/击杀、记分板快照、POV；新录入时按 POV 判断我方阵营 | 终局输出/承伤/参团率；未播完没有全场终局 |
| 截图 | 同一局七种分页截图，每种一张；补采或新录入都可用 | 终局 KDA、经济、输出、承伤、参团、评分、英雄、昵称、团队页指标和占比；新录入时默认左列 = 我方 | 过程时间轴、击杀事件、位置轨迹；新版装备名称 v1 不提取 |
| 回放（选填） | 1 份 `.abc`（可带 `.ope`） | 十人名单（阵营、真实槽位、昵称、entityId、英雄、评分）、胜负、胜/败方 MVP、版本/地图/帧数、同局配对；评分可直接补草稿 | 终局 KDA/经济/输出/承伤/参团/位置轨迹；1082 完整结算不在回放中 |

营地面板的 BP 是**终局名单**（`banHeros` / `pickHeros`），自动进入 BP 分析页的禁用、选用、阵容、分路与对手习惯统计；1–5 楼 pick 手序与一手方营地不提供，仍需在校对页人工补录，页面分档标注来源。已入库通道可用 `python tools/backfill_camp_bp.py` 从本地 `data/camp_details/` 重放补齐（幂等、自动备份），不需要重新爬取或重新审核。

仅营地路径需要：本局附件端关联一份录像 OCR JSON 报告；原始视频在“录屏采集”上传并后台识别，再导出报告关联到本局。该路径每局只需一段完整视频。OCR 新录入路径则是先有截图组或录屏报告、再把通道建出来，见上表「两种录入方式」。

## 英雄名单对比

截图上的英雄小字会读错。通道不是只靠单张图猜，而是把同一局的英雄名单汇总起来：

1. 回放 `.abc` 的英雄块（最可靠）。
2. 一份录像 OCR 报告的 lineups。
3. 表格里的英雄列。
4. 截图多页里的精确名/近似候选。

处理规则：

- 截图已有精确英雄，且名单里存在：保留。
- 截图只有候选，候选在名单中且未被占用：标记为 `roster-candidate`，仍需人工确认。
- 名单里只剩一个未分配英雄、草稿也只剩一个空缺：标记为 `roster-elimination`，这是排除法，不是头像猜测。
- 名单没有的英雄/重复英雄会保留冲突提示，不静默覆盖。
- 草稿表可直接手工改英雄和数值；修改后审核状态失效，必须重新审核。

## 跨来源草稿

草稿固定字段（当前）：

```text
hero
kills / deaths / assists
gold / damage / taken
participation / rating

# 扩展指标：截图（输出 / 生存 / 发育 / 团队页）或营地面板都能提供；
# 只作增强，缺失不阻止审核/保存，也不计入缺失清单。
cs / jungleGold / control / healing
towerDamage / damageConversion / takenPerDeath
```

每个字段保留：

```json
{"value": 9300, "raw": "9.3k", "source": "screenshot", "confidence": 0.97}
```

合并优先级：

1. 截图终局值作为基础（终局数据最直接）；七页里的扩展指标（补刀、野怪经济、控制效果、治疗量、对塔伤害、伤害转化比、每死承伤）同样从对应页进入草稿。
2. 表格补齐截图没有的字段；表格与截图不一致时保留截图值并记录冲突。
3. 回放补十人身份、真实槽位、昵称、胜负、MVP 和评分；录像补身份/时间轴。比分板行身份尚未可靠绑定，所以不直接把录像快照覆盖终局；KDA/经济/输出/承伤/参团仍以截图/表格/运行时为准，回放的部分金币/坐标只作证据。
4. 营地十人面板在最后合入，数值以面板为准（核心与扩展字段都会被面板覆盖）。`damage` / `taken` 取面板的 **对英雄输出 / 对英雄承伤**（`totalHeroHurtCnt` / `totalBeheroHurtCnt`），与截图「输出 / 承伤」页同口径；`totalHurtCnt` / `totalBehurtCnt` 含兵线野怪，不写进契约字段，只留在 `data/camp_details/` 供决策台等按需读取。
5. 手工修订覆盖一切，来源标为 `manual`，并写入修改日志。

**显示精度不算冲突**：截图/表格的 `raw` 原文只有 `66.1k`、`48%`、`1.2万` 这种显示精度时，与营地面板原值（66056 / 48.1）按精度比对；同屏读数不记冲突，差一个档位以上才留痕。

缺失清单按字段统计“10 人中缺几个”；不会把 3/5 的字段冒充团队合计。

## 人工审核与修改日志

- 复核人是本机文本，不是账号系统；默认 `local`。
- 审核时间由服务端写入。
- 草稿手工修订记录 `before/after`（字段、选手、值）。
- 任何来源变更或本局信息修改会**自动使审核失效**，必须重新审核。
- 只有必采材料齐全且 `review.status = reviewed` 才能保存到分析平台；审核与保存接口都重新检查必采材料。
- 保存动作写入 `data/matches/channel-<id>.json`，调用 `/api/analysis/reload` 后分析平台可读。
- 分析数据包中标明来源 `channel`，并提示“截图左右映射为 blue/red 仅用于展示，不代表真实红蓝方”。

## 页面

- `/#ingest`：通道列表、创建一局通道、来源状态、草稿缺失、审核/保存状态；营地拿不到的老局从这里「新录入一局（截图/录屏）」。
- `/#shots`：截图 OCR。上传识别后，每张结果卡片提供两个入口——「补采到已有对局」和「营地窗口外 · 新录入 → 新建一局并录入」。七页齐全才能新建；已补采过的组会标出来。
- `/#videos`：录屏 OCR。同样提供「补采到已有对局」和「新录入一局」两个入口；识别完成的报告可直接建档。
- `/#review/<id>`：
  - 本局信息（日期、对手、训练组、版本；OCR 通道还可改我方左右与胜负）。
  - 来源状态表：需要 / 已放入 / 状态 / 最近上传 / 解析完成 / 提示。
  - 四个放入口：表格、录像报告、截图组、回放记录。
  - 跨来源草稿：10 人 × 字段，可编辑，显示来源/缺失；核心 8 字段之外，扩展指标（补刀、野怪经济、控制、治疗、对塔、伤害转化、每死承伤）也进同一张表，来自截图对应页或营地面板，缺失不影响保存。跨来源冲突保存在 `draft.conflicts` 里供核对，不在单局复盘页重复展示。
  - 人工审核：复核人、备注、审核时间、保存到分析平台。
  - 修改日志：时间、动作、操作者、变更摘要。

## 本机 API

```text
GET    /api/channels
POST   /api/channels                      # {match:{...}, entry?:{mode:'camp'|'ocr'}}
POST   /api/channels/from-screenshots     # {imageIds:[...], date?, session?, opponent?, ownSide?, winner?} 新建 OCR 通道
POST   /api/channels/from-recording       # {recordingId, date?, session?, opponent?, ownSide?, winner?}  新建 OCR 通道
GET    /api/channels/{id}
PATCH  /api/channels/{id}                 # 本局信息
POST   /api/channels/{id}/screenshot      # {imageIds:[...], replace?} 默认与已挂截图并集合并
POST   /api/channels/{id}/table           # 原始 CSV/XLSX
POST   /api/channels/{id}/video           # 录像 OCR JSON 报告
POST   /api/channels/{id}/replay          # {replayId}
PATCH  /api/channels/{id}/draft           # {players:[...]} 人工修订
POST   /api/channels/{id}/review          # {reviewedBy, notes}
POST   /api/channels/{id}/save            # 写 kpl-match-data-v1 数据包
DELETE /api/channels/{id}
```

通道、来源原文件（表格/录像报告）进入完整备份与恢复；截图/回放引用现有图片和回放记录。

## 当前限制

- 本局附件端收一份 OCR JSON 报告；mp4 在“录屏采集”上传/排队识别。
- 本局表格只取第一张工作表，按项目十人模板逐局校验；多局往下追加（每局十行、对局ID不同），聚合表使用批量导入。
- 表格与截图按昵称/英雄匹配；昵称缺失或改名的行不会强行合并。
- 录像记分板行没有稳定的身份绑定，暂不覆盖终局 KDA；它提供英雄名单、时间轴和过程快照。
- 保存包是 `kpl-match-data-v1` 分析数据包，不是正式数据库比赛；正式比赛仍需工作台人工确认。
- 复核人是自由文本，不是登录账号；如需审计级身份，应增加本机账号/签名。

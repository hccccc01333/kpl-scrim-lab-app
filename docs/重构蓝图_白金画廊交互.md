## 1. 病根诊断（为什么"普通 / 既视感 / 重复"）

调研证据：
- **重复**：结论卡、对位卡、英雄池交叉、BP 手序在单局/跨局/大场/战队/选手/BP/英雄 7 个入口各画一遍；光结论卡就有 9 套类名（`md-hero#match-verdict`/`bgx-verdict-*`/`xw-exec-verdict`/`tb-verdict`/`hc-verdict`/…）。
- **死代码**：`cross-page.js` 有一整段大场详情（`detailHtml` 1419-1488 / `verdictText` 1397-1417），路由早已重定向到 biggame，代码还留着。
- **样式失控**：`interface.css` 30+ 个 `@import`，多条注释写着"未分层最后导入，盖过历史补丁"；`design-consistency.css` 2111 行靠页面选择器兜底。
- **蓝色混杂**：主题蓝 `#1f6fcf` 与图表蓝同值，硬编码蓝散布在 `teams-board-light.css`(67 处)、`design-panels.css`(33)、`match-redblue.css`(21) 等。
- **结论**：不是"板块太多"，是**同一份分析逻辑被复制多份 + CSS 用页面 ID 反复 1:1 覆盖**。

## 2. 新交互模型：焦点 + 镜头卡片流

### 2.1 结构

```
┌─────────────────────────────────────────────────────┐
│ 白金顶栏：赛事 · 焦点选择器 · 搜索 · 主题            │
├──────────────┬──────────────────────────────────────┤
│ 焦点对象栏   │  镜头卡片流（主工作区）               │
│ (左侧rail)   │  ┌─────────────┐ ┌─────────────┐     │
│              │  │ ① 结论镜头  │ │ ② 对抗镜头  │ →   │
│ • 这一局     │  │  白金卡框   │ │  白金卡框   │     │
│ • 这一系列赛 │  │  一句话判断 │ │  对位/经济  │     │
│ • 这个选手   │  └─────────────┘ └─────────────┘     │
│ • 这个战队   │  ┌─────────────┐ ┌─────────────┐     │
│ • 这个英雄   │  │ ③ BP 镜头   │ │ ④ 执行镜头  │     │
│              │  │             │ │             │     │
│ [+ 添加焦点] │  └─────────────┘ └─────────────┘     │
└──────────────┴──────────────────────────────────────┘
```

- **焦点对象栏**（左侧 rail）：替代原横向导航。选的是"我要看谁/哪场"，不是"我要去哪个功能页"。
- **镜头卡片流**（主区）：一组**统一定义**的分析镜头，卡片可横向/纵向滑动。镜头 = 结论 / 对抗 / 经济 / BP / 执行 / 阵容 等。
- **镜头是唯一定义**：一套镜头组件，焦点变化只换数据切片，不换镜头结构 → 根治既视感。
- **不违反红线**：镜头是统一分析维度（不是教练问题），焦点只是数据筛选器（不是按实体分页）。

### 2.2 镜头统一契约（吸收 atelier 的"判断"基因）

```
LensCard({
  grain:    'match' | 'series' | 'season',  // 只标口径，不切页面
  focus:    { type: 'team|player|hero|match|series', id },
  verdict:  { headline, tone, deltas[], signals[] },  // 结论先行/偏差/状态灯
  evidence: { n, source, caveat },
  children: [ ... ]  // 教练认可的原有分析板块，原样嵌入，不删
})
```

- 沿用现有口径：`RATE_MIN_N` 只决定"敢不敢下结论"、不藏数字；异常雷达不给主观严重度。
- 每个镜头就是一张白金卡片，结论大字在上、证据在下。

### 2.3 与旧结构的关系

- 旧 hash 路由（`#match/...`、`#cross/...`、`#bp` 等）**保留为兼容入口**，重定向到新的"焦点+镜头"视图并定位到对应镜头。
- 教练认可的板块（十人面板、应用池交叉、逐层推演、周报等）作为镜头的 `children` 完整保留。

## 3. 进门：新设备配置式卡片滑动

- 首次进入：金色全屏首屏 → 卡片流依次滑动：**赛事 → 本队战队 → 本队选手 → 采集 → 对手简档 → 完成**。
- **顺序判断**（调研结论）：赛事是技术硬门控（`GATED_NAV`），必须第一；本队最小建档（战队名/教练）在采集前；采集拉一局后才能从十人面板认人建档；对手简档放最后（只需名字/标签，忘了 ID 可先占位后补）。
- **差异化表单**：本队详细（巅峰分/A-B-C/擅长英雄/指挥/首发替补）；对手只需名字+巅峰千强队/百段队标签，ID 可后补（现有占位体系 `待命名选手 #N` / `待命名战队 #N` 可复用）。
- **必须可跳过**：历史上把首页整页换成向导被反馈"像死胡同"——每一步都留"我已有数据，直接进首页"出口。
- **与 tour 协调**：首次自动弹的 8 堂课教程要在向导未完成时不弹。

## 3.5 产品定位与数据管理层（2026-11-22 与教练探讨定稿）

> 定位收敛：**赛训是地基（底座数据），之上立两根柱子——数据管理、数据分析**。
> 产品是「赛训领域专用的可视分析工作台」，不是通用 BI，不是"带图表的网站"。
> 数据层底座已成型（`workspace_store.py` 关系模型 + `channels` 采集流水线），本章只定前台结构。

### 3.5.1 三套档案 + 一个观察视图

| 档案 | 必填 | 字段 / 特点 | 转会行为 |
|---|---|---|---|
| **本队选手档案** | 真实姓名 / 比赛ID / 分路等 | 完整：巅峰分、五路段位、英雄战力（点头像选）、首发/替补标签、性格、教练自定义风格标签 | 点「转会」→ 移入对手选手档案 |
| **对手选手档案** | 只需比赛正式ID | 精简模板，其他选填；保留"每个交手过的选手的训练赛+正式赛数据" | 别人转入 → 字段变必填、升格为本队档案 |
| **试训档案**（独立系统） | 姓名 / 主打分路 / 风格 | 按**时间窗**切块（如 10/27–10/30），每块含巅峰分、段位、英雄战力、该段用英雄、比赛指标；可在试训系统内横向对比各试训者 | 转正后**留在试训系统**，不迁出、不并入正式档案，互不干扰 |

- **试训档案 ≠ 正式档案**：试训是独立系统，转正后原样留着，正式档案另起，两份隔离。
- **试训采集复用主链路**：采集处勾「加入试训系统」即可，不另起采集链路；有日期落进赛事区间的试训对局必须**排除**，不被赛事归集。
- **档案回归纯事实**：档案只放身份/属性，**不放赛后指标率**。指标查看脱离档案独立成视图。

### 3.5.2 本队选手指标观察视图（组件层第一个实例）

- **排版**：默认单栏，可切两栏/三栏做**对位排版**。
- **栏内容**：本队选手 / 对手选手 / **KPL 职业选手数据作"高手对位"基准**（新增基准数据源，现有 BP 包 KPL 数据可评估复用）。
- **指标**：用赛训组自己的指标规则（`grade-rules`）。
- **筛选维度**：BO 赛制（BO1/3/5/7）× 赛事 × 比赛类型（训练赛/正式赛）× 时间窗。
- **趋势**：巅峰分、段位、英雄战力等属性**也进时间变化**（教练确认"可以加趋势图"）。
- **一次看多人**：解决"教练一个个点开档案看很麻烦"的痛点——选 N 个选手叠加曲线。
- 该视图的交互引擎（选对象→选指标→选筛选→出对比）与后续"多场对局分析"共用，建一次、多处复用。

### 3.5.3 赛事与时间口径

- 赛训组自建赛事：填**赛事名 + 起止时间**，该时间段内的训练赛**按录入日期**自动归集到赛事下（战队会提前训练，故按录入而非比赛发生日）。
- 赛事另设**「正式比赛时间」**字段，专门限定正式比赛的范围——赛事有两个时间口径：训练时间（卡片上写作「训练起始 / 训练结束」，按训练日期） / 正式比赛范围（「正式比赛起 / 正式比赛止」）。
- 切换赛事 = 切换"当前围绕哪个赛事看训练赛"，驱动全站门控。
- **归集边界规则**：
  - 赛事时间段重叠 → 建时警告但不禁止，教练自行负责。
  - 未被任何赛事覆盖的训练赛 → 进「未归档」区，可见、可手动补挂，不因不属于当前赛事而消失。
  - 改赛事时间区间 → **重新计算**归属，不写死。
  - 「赛事」与「比赛类型（训练赛/正式赛）」是两个独立维度，不可合并。

### 3.5.4 数据导入

1. 现有采集链路（王者营地 / 截图 / 录屏 / 回放）：已成型，保留。
2. **正式比赛线上表格录入界面**（新建）：结构化字段录入 + 支持贴官方回放赛后数据图；先以线上表格为主，OCR 后续评估。
3. 试训数据：复用同一采集，勾「加入试训系统」。

### 3.5.5 赛后笔记

- 挂在**单局**上；后续扩展笔记日历、重点关注对局。

### 3.5.6 赛训规则中心（2026-11-22 定稿）

> 组合 / 英雄标签 / 好坏判定 / 克制关系 / 阵容标签本质是同一类东西——**赛训规则库**：教练告诉系统"怎么看比赛"的知识。
> 收拢成统一入口「赛训规则中心」，共用一套导入/导出/历史/回滚（扩展现有 `config-tools.js`），不散成五个设置页。
> 现状：组合池 / 字段规则 / 阵容标签已有界面；英雄标签、克制关系只有数据+算法无界面，需补。

**统一规则条目契约**：
- **生效时间**：按**赛事正式比赛时间**算（教练拍板）。分析时对局按所属赛事的正式时间取当时生效的规则版本，保证历史结论可复现。
- 每条规则带生效时间窗 + 变更历史 + 回滚。

**子规则分类**：
1. **英雄组合体系**：双人/三人/五人合成一套，按人数分层，一处维护（原组合池 + 阵容标签合并）。
2. **英雄标签**：基础标签（五路12类）**可直接编辑**（教练拍板，不做只读分层），赛训组自己维护。
3. **字段好坏判定**：现有 `grade-rules.js`（分路×字段四档阈值），纳入规则中心。
4. **克制关系**：带方向/强度/分路；**版本维度改用"赛事"**（教练拍板）——1对1、1对多、多对多，英雄克制英雄与组合克制组合分开存。
5. **阵容标签**：**纯表格自填自改，不做口述识别功能**（教练澄清："口述"是其向赛训组收集标签的方式，不是产品功能）。
6. **新增规则**：异常判定规则、指标口径/计算公式、风格标签体系等。

### 3.5.7 页面构成现状（只读调研 2026-11-22）

- 45 个可达页：分析 26（58%）/ 赛训管理 12（27%）/ 采集整理 7（16%）——"分析为主"成立，但管理+采集 42%，是"分析前台 + 较重中台"。

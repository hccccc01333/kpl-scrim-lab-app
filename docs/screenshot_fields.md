# 赛后截图字段契约 v1（新版分页 UI）

本文定义训练赛平台从**赛后结算截图**固定提取哪些字段。字段本身由平台维护，赛训组围绕这套字段准备截图和表格；识别结果只是候选，确认后才能进入正式统计。

与旧版 `ocr.py` 的双列五行布局不同，本文对应现在带底部页签的赛后 UI：

```text
总览 / 表现 / 数据 / 输出 / 生存 / 发育 / 战绩 / 团队
```

截图只收赛后结算页。局内 HUD、加载页、BP、个人主页等继续由录像 OCR 处理，不在这里重复开口。

## 结论（基于 7 张真实样本）

- 已实现新版分页 OCR：`postgame_ocr.py` 本身只读；工作台“截图采集”页把候选写入本机 `postgame_images`，不写正式比赛。
- 7 张样本实际来自 **3 局不同比赛**，不能拼成一局：
  - `01-score.png`：2026-06-17 12:25，18:52，33:34，胜利；装备型战绩页。
  - `02-kda.png` ~ `06-output.png`：14:26，同一套十人阵容；分别是战绩(KDA占比)、发育、生存、数据、输出五个页签。
  - `07-team.png`：另一套十人阵容，团队页签；没有比分和日期。
- `02-06` 五页可以合并成一局：比分 14:26，五人击杀合计左右各 14/26，与比分一致；字段并集完整到 10 人。
- `01`、`07` 各自单独成组，不能并进 `02-06`。
- 要冻结“同一局全页签”的端到端样本，还需要**同一局的战绩+数据+输出+生存+发育+团队六页**；当前 `02-06` 缺团队页，`07` 是另一局。
- 新版装备图标没有进入 v1 固定字段；只保留战绩页的截图和人工核对。

## 页面类型

| pageType | 对应页签 | 页面特征 | 比赛字段 | 选手字段 |
| --- | --- | --- | --- | --- |
| `score` | 战绩（装备型） | 顶部有胜负/比分；行内有 KDA、经济、装备、评分 | 日期、时间、时长、模式、胜负、比分 | 昵称、英雄、评分、称号、MVP、击杀、死亡、助攻、总经济 |
| `kda` | 战绩（KDA占比型） | 列头为 击败/死亡/助攻；每列有数量和占比条 | 比分（如果页头可见） | 昵称、英雄、评分、称号、MVP、KDA、KDA 占比 |
| `data` | 数据 | 列头 输出伤害/承受伤害/总经济/参团率 | 比分（如果页头可见） | 昵称、英雄、评分、称号、MVP、输出、承伤、总经济、参团率、三项占比 |
| `output` | 输出 | 列头 输出伤害/伤害转化比 | 比分（如果页头可见） | 昵称、英雄、评分、称号、MVP、输出、伤害转化比、输出占比 |
| `survival` | 生存 | 列头 承受伤害/每死承伤 | 比分（如果页头可见） | 昵称、英雄、评分、称号、MVP、承伤、每死承伤、承伤占比 |
| `farming` | 发育 | 列头 总经济/野怪经济/补刀数 | 比分（如果页头可见） | 昵称、英雄、评分、称号、MVP、总经济、野怪经济、补刀数、三项占比 |
| `team` | 团队 | 列头 参团率/控制效果/治疗量/对塔伤害 | 比分（如果页头可见） | 昵称、英雄、评分、称号、MVP、参团率、控制效果、治疗量、对塔伤害、三项占比 |

`score` 和 `kda` 都显示“战绩”页签，只是当前样本出现了两种内容形态；两者都归入固定页型，不把装备型当成另一个数据源。

### 三类来源的分工

| 来源 | 能提供 | 不能提供 |
| --- | --- | --- |
| 赛后截图 | 终局 KDA、经济、输出/承伤、参团率、团队页指标、各项占比、英雄/昵称/评分/称号 | 过程时间轴、击杀事件、位置/轨迹、装备名称（新版 v1 不支持）、本队阵营 |
| 回放录像 | 局内计时、团队金币/击杀、记分板快照 KDA/累计金币、铭文/装备候选、POV 片段 | 终局输出/承伤/参团率（画面不显示）、未播放完时的全场终局、操作者身份 |
| 赛训表格 | 赛训组自己统计的原始列和聚合列，可包含跨局胜率、英雄池、训练目标等 | 不自动证明同一局、不自动绑定选手 ID；原始/聚合必须按 grain 分开 |

工作台数据库负责本队阵营、选手 ID、对手、位置等人工确认字段；三条只读来源都不能替代这些确认。

## 固定字段

### 比赛

| 字段 ID | 含义 | 单位/取值 | 来源页 | 规则 |
| --- | --- | --- | --- | --- |
| `match.date` | 比赛日期 | `YYYY-MM-DD` | 战绩 | 缺失为空，不猜 |
| `match.time` | 比赛时间 | `HH:MM` | 战绩 | 缺失为空 |
| `match.durationSec` | 对局时长 | 秒 | 战绩 | `18:52` → 1132 |
| `match.mode` | 模式 | 文本 | 战绩 | 如 `5v5排位`；`未开始匹配` 是匹配提示，不是模式 |
| `match.result` | 胜负 | `win` / `loss` | 战绩 | 只在页面出现“胜利/失败”时填写；不从比分推断 |
| `match.score.left/right` | 页面比分 | 整数 | 所有页头可见时 | 校准样本中等于双方击杀合计；合并后校验 |

### 选手身份与荣誉

| 字段 ID | 含义 | 规则 |
| --- | --- | --- |
| `player.side` | 截图左/右 | 不是蓝/红；本队阵营仍由工作台确认 |
| `player.slot` | 行号 0–4 | 从上到下，不是分路 |
| `player.nickname` | 打印昵称 | 原样保留；不是稳定 ID；需与名单关联 |
| `player.hero` | 英雄 | 只接受与本地英雄目录**精确同名**且置信度足够的名字 |
| `player.heroStatus` | 英雄识别状态 | `exact` / `auto-matched` / `uncertain` / `unreadable` / `manual` |
| `player.heroCandidates` | 英雄候选 | 近似名/前缀候选，必须人工确认 |
| `player.rating` | 赛后评分 | 一位小数 |
| `player.title` | 称号 | 如“银牌中路”；是荣誉，不是分路 |
| `player.mvp` | MVP | 布尔值 |

## 2026-11-02 完整七页签验收

样本路径：`data/screenshots/samples/20261102_1559/`，同一局 5v5 排位，27:6、11:33、2026-11-02。七页分别是战绩（装备型）、战绩（KDA 占比）、数据、输出、生存、发育、团队。

- 合并结果：1 组、7 页、10 人；必采页（战绩 + 数据 + 团队）齐全，建议页也齐全。
- 英雄：跨页并集 10/10；昵称 10/10；比分 27:6 与双方五人击杀合计一致。
- 必采/建议页缺口由 `checklist` 给出；`readyForDraft=true` 时才建议生成草稿。
- **KDA 权威页是 KDA 占比页**。装备型战绩页的 KDA 列更小，可能把等级/奖牌读进数值；合并时 KDA 页优先。
- **KDA 占比校正**：若击杀合计与比分不符，或死亡/助攻与占比明显矛盾，平台用 KDA 页的占比 + 团队比分做整数分配。例：右 1 击杀 7、占比 17%、团队 6 → 校正为 1；右 2 死亡 17、占比 26%、团队 27 → 校正为 7。原值保留在字段 `originalValue`，并写组内提示。
- **显示精度不算冲突**：数据页写 `8.7k`、战绩页写 `8697` 时，按显示精度兼容，保留精确值 8697，不再生成 17 条假冲突。
- **Mimo 精读是可选层**：只读英雄名/昵称列；整页结构化抽取会错列，不作为默认。没有 Mimo 时，上述合并和校正仍可完成。
- 该样本的右 1/右 2 KDA 误读是现有快速 OCR 的真实边界；校正只在这些页同时提供 KDA 占比和比分时生效，且必须保留原值供核对。

## 同局合并规则

1. 有日期/时长时，日期或时长不同，不合并。
2. 双方比分都存在且不同，不合并。
3. 没有比分时，用同一 `side/slot` 的昵称、英雄、评分计算阵容重合；重合不足 7/10 不合并。
4. 合并只做字段并集：同一字段值一致保留；冲突时保留置信度更高者并写警告。
5. 英雄只有精确名可以跨页补齐；候选/未读不自动补。
6. 同局合并结果保留 `pages` 来源列表，任何字段都能追溯来自哪一页。
7. 不同比赛即使阵容相似，也必须有比分/日期/时长之一支持；否则宁可不合并。

## 固定字段的边界

不进入截图核心字段：

- 过程时间轴、击杀事件、推塔/龙/主宰、技能冷却、血量/蓝量、视野、经验、BP、分路、选手 ID、本队阵营、对手、赛段、版本。
- 装备名称：新版装备图标未进入 v1；只保留截图，人工核对。
- 队伍合计：截图没有直接给团队合计；同队五人字段齐全时由平台派生，并记录公式，不作为截图原始字段。
- KDA 比率、GPM/DPM/TPM、经济/输出/承伤占比的二次计算：派生字段，不覆盖页面显示值。
- 控制效果的单位/口径（次数、时长或评分）仍按页面原值保存，待游戏内定义确认后再决定是否换算。

其他语义约束：

- 页面左/右不是蓝/红。`left/right` 只描述布局；本队阵营必须由工作台确认。
- 比分是页面显示值，校准样本中等于双方击杀合计；合并后必须做 KDA 合计校验。
- 昵称是打印文本，不是稳定 ID；赛训组仍需把昵称映射到名单。
- 称号（银牌/金牌/铜牌）不是分路；不能拿来推断位置。
- `未开始匹配` 是匹配状态提示，不是模式；OCR 不会把它写入 `mode`。
- 数据页/输出页/生存页/发育页也可能有比分，但没有日期/时长/胜负；不能单独归档。

## 采集要求（赛训组）

同一局至少提供：

```text
战绩页（带日期/时长/胜负） + 数据页 + 团队页
```

推荐再提供输出、生存、发育页，得到完整并集。

- 原图，不裁切、不拼图、不压缩转发；保留顶部页头和列头。
- 建议 1600×900 或更高、16:9；至少 1280×720。
- 同一 UI 版本、同一分辨率；中文 UI。
- 页面底部页签、双方/对位切换可见；确保选的是“双方”，不是只显示对位的两行。
- 不要带“未开始匹配”弹层、加载动画、聊天或系统弹窗；如果无法避免，至少保证表格和页头不被遮挡。
- 每局所有页签都来自同一局；截图之间不要混局。
- 截图文件按 `日期_对手_页签.png` 命名，便于人工核对。

如果只能提供一张，优先“战绩页”；它能给日期、时长、胜负、KDA、经济，但给不了新版装备名称。

## 工作台入口

新版分页截图已经接入工作台左侧栏的“截图采集”（`/#screenshots`）：

- 上传原图到现有 `images` 表，识别结果单独存到 `postgame_images`，不会覆盖旧版比赛校对的 `images.ocr`。
- 页面提供 7 个固定输入口：战绩（装备型/KDA占比）、数据、输出、生存、发育、团队；每个入口带 `web/capture-guide/` 下的截图示意图。也保留自动识别/批量上传，放错页签会提示。
- 页面显示每个页签的页型、比赛信息、逐人字段、字段覆盖和警告；同一局多页自动成组，不同比赛分组展示。
- 每组可导出 `kpl-postgame-screenshot-v1` JSON；原图和结果都进入完整备份。
- 分组内展示派生分析：截图左右团队汇总、完整字段的左右对比、KDA/经济/输出/承伤/团队指标、选手排行和覆盖警告。只有 5/5 齐全的字段才作为团队合计，部分字段会标样本数。该分析是采集候选预览，不进入正式统计；正式分析平台仍只读已确认比赛、数据包和表格导入。
- 没有采集数据时可载入 7 张示例截图查看分析；示例结果带 `demo` 标记，可单独清除，不进入正式统计。
- 每组可生成比赛草稿，带走日期、比分、KDA、经济、输出、承伤、参团、评分与英雄；走采集通道的「新建一局并录入」时，输出 / 生存 / 发育 / 团队页的扩展指标（伤害转化比、每死承伤、补刀、野怪经济、控制、治疗、对塔）也会进入通道草稿，可在校对页修改并随正式数据包保存。扩展指标缺失只作增强缺失，不影响审核/保存。
- 生成草稿不会自动确认入库；本队阵营、队员、英雄和正式确认仍需在比赛校对页完成。
- 单页重新识别、移出采集结果都在本机完成；移出采集不会删除原图。

本机 API：

```text
POST   /api/postgame/images/{image_id}/ocr[?refresh=true]
GET    /api/postgame/images
DELETE /api/postgame/images/{image_id}
```

`GET` 返回 `images`（逐图摘要）和 `groups`（同局合并 bundle）；识别结果表为 `postgame_images`，原图仍在 `images`。

## CLI 与验证

```powershell
python scripts/postgame_screenshot.py `
  "战绩.png" "数据.png" "输出.png" "生存.png" "发育.png" "团队.png" `
```

- CLI 不写数据库、不写工作台，只输出候选；工作台采集页使用同一识别器，把候选保存到本机 `postgame_images`。

## 当前限制

- 英雄名是小字；现在用原图分辨率 + 英雄名竖列条 OCR + 英雄目录唯一近似匹配，示例组 `01` 补到 10/10（其中 `澜` 完全无 OCR 输出，示例中按画面校正）。不能为了凑齐而按头像/皮肤猜；同一局放入采集通道后，会先用回放/录像/表格名单自动比对。截图采集页的 10 人明细仍保留下拉作为兜底。
- 装备图标（`01-score.png`）不在 v1；需要时再按图标库做候选，仍需人工确认。
- 日期、时长、模式、胜负只在战绩页；其他页只有比分。
- `07-team.png` 没有页头和比分，不能单独归档；它证明团队页字段可读，但不能替代同局团队页。
- 样本是裁剪图，底部导航缺失或只露一部分也能识别（靠列头），但生产采集仍建议全屏原图。
- 识别值是候选；低置信度、冲突、缺失都要在工作台复核。

## 治理

- 核心字段 ID、页型、单位和版本号由平台上游维护；赛训组围绕字段改自己的表格和采集流程。
- Agent 可以写适配器、分析器、候选识别器，但不得擅自改核心 schema；需要新字段时先提 schema 变更。
- 截图/录像/表格三条来源共用同一套字段语义；新增页型或字段必须升 schema 版本。
- 本模块只读、本地运行，不调用云端、不写数据库。
